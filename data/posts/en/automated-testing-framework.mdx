## The problem: evolving an existing system

I have contributed to this suite since September 2025 as part of my software engineering apprenticeship. The project already had Selenium business scenarios, page abstractions and Jenkins pipelines.

The challenge was both to make browser interactions more reliable and to support uses beyond nightly builds. Users needed to select a scenario, supply parameters and retrieve its outcome without operating Jenkins or duplicating the scenario in a second engine.

## The central choice: separate a scenario from its trigger

The same scenario should run from CI or a user request. Its parameters and business steps should not depend on the trigger.

```mermaid
flowchart LR
    CI[JUnit / Maven / Jenkins] --> CORE[Shared test foundation]
    UI[Angular interface] --> API[Asynchronous Spring Boot API]
    API --> CORE
    CORE --> PRE[Preconditions and preparation]
    PRE --> SEL[Selenium and business scenario]
    API --> DB[Execution history]
```

This is a responsibility diagram, not an exhaustive class map. The shared foundation handles parameters, preconditions, preparation and cleanup, and result production.

### Reusable Selenium abstractions

Much of the work preceded the API: extracting common operations instead of repeating table reading, processing tracking or element lookup in every scenario.

Table abstractions were made generic and progressively integrated into pages. Unit tests against test HTML pages cover these behaviors. A shared component becomes easier to evolve, but changes still need checking across the scenarios that use it.

### Asynchronous execution for the web

An HTTP request should not remain open throughout a Selenium run. The API validates parameters, creates an execution and submits work to a background executor. The interface can display its states: queued, running, successful, failed, skipped or cancelled.

Typed parameters describe the expected inputs and allow validation before launch. History retains information for understanding a run and retrieving its logs or screenshots.

## The Angular interface: making tests usable

I started the interface in early August 2026 and built it end to end. It includes:

- A scenario catalogue and parameterized launches.
- Active executions, recent results and per-test activity.
- Execution logs and screenshots.
- Test scheduling, activation and deletion.
- Authentication, user preferences and execution cancellation.

The REST client is generated from the OpenAPI description. This lets me focus on user flows and application state while keeping types aligned with the server contract.

### WebSocket notifications and REST details

The interface combines WebSocket/STOMP notifications with REST reads: after a status-change notification, it fetches execution details through REST and updates its lists.

```mermaid
sequenceDiagram
    participant UI as Angular
    participant API as REST API
    participant WS as WebSocket/STOMP
    UI->>API: Request execution
    API-->>UI: Execution identifier
    WS-->>UI: Status-change notification
    UI->>API: Fetch execution details
    API-->>UI: Updated state
```

The notification does not carry the full result. The backend remains the source of state. Server-side WebSocket publishing is a team contribution; I implemented its frontend integration.

## Tradeoffs and limitations

**Preconditions and isolation are different problems.** Checking whether a scenario can start avoids some unnecessary executions. It does not guarantee that concurrent tests never mutate the same data. Data preparation, cleanup and isolation remain necessary.

**Restart recovery is simple.** An October 2026 change requeues persisted executions that are still active at startup. This does not guarantee exactly-once execution: an interrupted scenario may already have produced side effects.

**Parallelism must respect the application under test.** A thread pool does not remove business conflicts, browser constraints or the capacity limits of a shared environment.

**Reliability also depends on scenarios.** Better orchestration does not automatically fix a fragile selector or an incorrect wait. Work on reusable abstractions and related tests remains essential.
